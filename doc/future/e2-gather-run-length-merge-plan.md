# E2 执行方案：实例化合并 —— 静态烘焙（S1）+ 显式实例组（S2）

> **版次**：v2（2026-10-07）。**v1 的「每帧动态段合并（形态 A/B）」已按用户 2026-10-07 拍板作废**：
> 每帧动态合批看着花，实质很糟 —— 它必须在**运行期**满足"合并命令的实例行恰好连续"这条硬约束，
> 而运行期的行号是 `atomicAdd` 分出来的（无序）⇒ 要么加一趟扫描/前缀和（贵），要么被 64 实体块边界切碎。
> 而**绝大多数几何基本不动**。改为**「改变时烘焙」**：静态集合一次分类合并好、之后按桶做一次 instance 渲染；
> 动态项完全不合；开发者可**显式指定实例组**（粒子 / Foliage / 挂在会动父体上的静态附件）。
>
> **来源**：`doc/backlog.md` E 线 E2（2026-10-05 用户留置）→ 2026-10-07 用户重定方向（本稿 v2）。
> 现象与机制层规格仍见 `doc/future/entity-rows-gpu-cull-plan.md` §8.10 §八 / §9。
>
> **状态**：四条已拍板（§2）、S2 两条待拍板（§7）；**T1 判据前置可立即开工**。

## 0. 现象与目标

| 口径 | CPU 账（历史基线） | 形态 B 接管（现状） |
|---|---|---|
| `GPUDrivenCull` 的 64 个同几何 cube | 1 条命令（Y=64） | **64 条命令（Y=1）** |

- 像素**完全一致** ⇒ 现有像素/对账判据对此**永远无感**；差的是命令数（ICB 条目、per-draw 参数行、
  每条 mesh 命令的固定启动开销）。
- **v2 目标**：让"同一类东西"在**布局层面**成组 —— 静态集合在**改变时**一次烘焙成"桶 × 键"的命令表；
  显式实例组的成员槽位稳定、每帧只写数据。**取消"每帧动态合并"这个负担**。

## 1. 已核实的现状（事实基座，逐条给 path:line）

1. **命令写法**：`ShaderLibrary/ecs/entity_gpu_cull.glsl` gather 尾部
   `DrawIndirectCommandsRef(pc.indirect_commands_addr).commands[row] = DrawMeshTasksIndirectCommand(group_count_x, 1u, 1u);`
   —— `row = binfo.row_base + slot`，`slot = atomicAdd(counters.counters[block_base+batch], 1u)`。
2. **Y 维度本来就是实例维度**（机制已在）：`MeshShaderHeaderGen.h:123`
   ⇒ `#define gl_InstanceIndex (draw_params.first_instance + gl_WorkGroupID.y)`
   ⇒ Y=桶内成员数、`first_instance`=桶行基址，即得"一条命令画 N 个实例"。
3. **实例号直接当行号用（本任务的硬约束）**：`MeshShaderVaryingGen.h:148` ⇒ `data_id = gl_InstanceIndex`；
   `RenderItemResolve.glsl` 直通模式以 `gl_InstanceIndex` 取行；`fragDataIndexID[vid/3u] = gl_InstanceIndex`
   （`:115`）⇒ **一条合并命令的 Y 个实例，其行号必须恰好连续**（`first_instance + 0 … + Y−1`）。
   **S1/S2 靠"构建时排行"天然满足**；每帧动态合并则要额外扫描才能满足（§8）。
4. **行/槽现状由 `atomicAdd` 决定**：数量确定、**相邻性不受保证** ⇒ 只改命令写法必然错。
5. **draw 消费的"条数" = 每批计数值**：`PipelineMaterialRenderer.cpp:35-56`
   ⇒ `vkCmdDrawMeshTasksIndirectCount(first = slice.row_base, count = 本批那一格, max = slice.capacity)`。
   ⚠ 该格今天兼任两个角色（gather 的行槽计数 / draw 的命令条数）；S1/S2 下**桶的行号不再走运行期分配**
   ⇒ 该格退回**纯命令条数**语义（契约要明写）。
6. **批 = 同管线（不是同几何）**：`PrimitiveBatchPipeline.cpp:969-977`（`capacity = b->items.size()`，
   批键 = `b->key.shader_program`）⇒ 一个批内可含多种几何；`topology`/`group_size` 是**批级常量**
   （随 `SetBatchLayout(..., topology, group_size)` 下发）⇒ 逐项键退化为 `geometry_id`
   （+ geometry 行的 `index_base/vertex_base/is_indexed`，见 §6 R2）。
7. **判据基座已在**：`CPUCullReferenceSystem`（`src/ecs/core/DefaultSystems.cpp:112` 注册）已
   `SyncForParityReadback()` + `MapCurrentBatchCounters(0)` 读回每批计数与溢出槽
   （`src/ecs/support/CPUCullReferenceSystem.cpp:109` 起），并做三方值链对拍。
8. **⚠ CPU 绘制路径已整条删除**（T4c4；未接管 = fail-fast 不画）⇒ §8.10 里"CPU 1 条（Y=64）"是**历史事实**，
   不能当活判据的对照臂 ⇒ 期望值改为**引擎侧按构建/变更数据推算**（§4）。
9. **静态判定源已在引擎里**：`TransformAccessor::IsStatic()`（`TransformAccessor.h:126-127`）；
   先例 = CSM 条带路径用 `mobility_filter=Static` 筛静态 caster。

## 2. 用户拍板（2026-10-07）

| # | 决定 | 落地含义 |
|---|---|---|
| 1 | 静态判定源 = **现成的 `IsStatic()`** | 不新增"作者标记"机制；复用 mobility |
| 2 | 桶粒度 = **key + 空间 chunk** | 桶 = 几何/管线键 **× 空间分块** ⇒ 桶级剔除才有分辨率 |
| 3 | **动态项完全不合** | 不做 A（块内合并）、不做 B（全局扫描）；动态项保持现状（每项一条命令） |
| 4 | 静态项 **L2W 走独立池**（不按帧槽分份） | 静态 L2W 每帧相同 ⇒ 单份（省 8× 内存）；新增"静态池不轮转"语义 |

**A / B 处置 = 「已评估未选」**（不是被证伪）：见 §8 的量化。若将来出现"每帧都在变且必须最小命令数"
的场景再回看；**当前一律不做**。

## 3. 目标形态

### S1 —— 静态实例烘焙（主力）

- **触发**：静态集合**变更时**（作者改场景 / 批量导入完成 / 显式 `RebuildStaticBatches()`），**不是每帧**。
- **产物**（一次性，帧间复用）：
  - `静态命令表`：每个**桶**一条 `{X=组数, Y=桶内成员数, 1}`；桶 = `key × 空间 chunk`；
  - `静态行池`：每桶的实例行**构建时排好** ⇒ **行天然连续**（正是 §1.3 的硬约束，构建期自动满足）；
  - `静态 L2W 池`：**单份**（拍板 4）。
- **每帧代价**：**桶级剔除** —— 桶 AABB 对视锥 ⇒ 不可见桶把该命令的 `Y` 置 0
  （indirect 命令 `Y=0` = 不画，**无需压缩命令列表**）。代价 = 桶数量级（几十~几百），与实例数无关。

### S2 —— 显式实例组（开发者指定；回答 Ext：会动的父体挂静态模型）

**场景**：FPS/RTS 里大量敌方士兵，头盔/手雷是静态模型、位置在动（挂在会动的父体上）——显然可合批，
但它们的 L2W **每帧都变**。

**答案**：与 S1 **同一套机制**，区别只在"哪一面被冻结"：

| 可变面 | S1 静态烘焙 | S2 显式实例组 |
|---|---|---|
| ① 成员集合 / 布局（谁属于哪组、行怎么排） | 构建时冻结 | **构建时冻结**（同一机制） |
| ② 每成员的每帧数据（L2W / 参数） | 也冻结（本来就不动） | **每帧写**（O(成员数) 紧凑写，**无需重排**） |

- **开发者给的"索引" = 稳定槽位**：`InstanceGroup{ key, geometry, 成员容量 }` + 每成员一个
  `(组 ID, 组内序号)` ⇒ **行号 = 组的行基址 + 序号**（稳定）⇒ 每帧只按"谁动了"写那些行
  （可与现有 `TransformSystem` 的脏行机制打通）。
- **成员增删**：预留空槽 + 每成员"有效/可见"标志（mesh shader 早退、emit 0 顶点）⇒ **增删不重建布局**
  （士兵死亡/生成就是此场景）。这是 S2 相对 S1 多出的必需件。
- **剔除粒度**：默认桶级（同 S1，`Y=0` 跳过）；**可选**逐实例（靠上面的 per-instance flag 在 mesh 内早退
  —— 省顶点但省不掉命令启动）。
- **每帧数据池**：S2 的行池**按帧槽分份**（每帧都在写），与 S1 的单份静态池是两条独立池/生命周期。

### 动态项与其它

- **动态项（非 `IsStatic`、未加入任何显式组）：完全不合**（拍板 3），保持现状。
- **粒子 / Foliage**：本质 = "S2 + 程序化 per-instance 数据源（粒子缓冲 / 密度图）" ⇒ 属 S2 的数据源扩展，
  不在本任务内；本任务只把 **S2 的机制（稳定槽位 + 冻结布局 + flag 增删）** 建起来。

## 4. 契约与判据

| 现契约 | 变更 |
|---|---|
| 「命令 = 每项一条、Y=1」（§9 M3） | S1/S2：「命令 = 每桶一条，Y = 桶内有效成员数（可 0）」 |
| 「Σcount == 批内项数」（§8.10 §五） | S1/S2 组：「**命令条数 == 桶数**」+「**ΣY == 组内有效成员数**」；动态项口径不变 |
| 行槽由 `atomicAdd` 运行期分配 | S1/S2：**行号 = 组行基址 + 稳定序号**（构建期定）；每批计数格退回**纯命令条数**语义 |
| 所有按帧数据表按帧槽分份 | S1 静态池 = **单份**（新语义，写进契约与池注释）；S2 池按帧槽分份 |

**判据**：
1. **命令数**（draw 实际消费条数）：静态 64 cube ⇒ **1 条**；
2. **ΣY == 组内有效成员数**（读 ICB 切片内命令求和）；
3. 现有全套不变：三方像素全等 / `不一致=0` / `overflow=0` / 0 VUID / 八台架摘要逐位；
4. **烘焙次数 == 变更次数**（单调计数器差分 ⇒ **离线可复核，不受 vsync/时序干扰**）；
5. **桶剔除正确性**：桶级剔除后的可见实例集合 == 引擎侧逐实例剔除的集合（对拍；桶不变更时恒等）；
6. **台架**：扩 `GPUDrivenCull`（`GC_*` 家族已在）：`GC_BAKE=1` 打印
   `桶数=… 命令数=… ΣY=… 烘焙次数=…`；加"静态 + 显式组 + 动态项三者共存"的用例。

**期望值来源**：引擎侧按构建数据推算（**不依赖已删除的 CPU 绘制路径**）——
桶数 = 构建时按 `key × chunk` 分组的组数；`ΣY` = 有效成员数。

## 8. 附录：为什么"每帧动态合并"被否（量化留档）

- **形态 B（全局扫描）** = 6 pass + 4 scratch：P1 判可见/取键（写 `cull_scratch[entity]`）→ P2 块内按批掩码前缀和
  （写 `block_sum`）→ P3 块和扫描（`block_base`）→ P4 落 rank + 键按 rank 排好（`key_by_rank`）→
  P5 段检测 + 段索引扫描（`run_table`，段首写命令）→ P6 写四张行表。实体轴被扫 3 遍；**行槽分配从
  `atomicAdd` 换成扫描** ⇒ 与 M4（切片 4 行对齐 / 每批计数 / overflow 末位槽 / `Σcount` == 项数）正面相撞；
  新 scratch 若不按帧槽分份即引入新的跨帧覆写面。
- **形态 A（块内合并）** = 单 pass（workgroup 内 run-length encode + 每块每批一次原子取段基址），
  但**段被 64 实体块边界硬切**：512 个同键 cube ⇒ 8 条（理想 1 条）；批内实体号交错时 ≈ 不合并。
- **共同病根** = 在**运行期**做布局，还要满足 §1.3 的"实例行连续"。烘焙把布局挪到"改变时"
  ⇒ 顺序/连续性、扫描、前缀和、原子序**全部消失**，且判据变成可离线复核的"烘焙次数 == 变更次数"。
